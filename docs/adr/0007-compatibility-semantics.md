# 0007 契约兼容性方向与判定规则

- Status: Accepted
- Date: 2026-11-10

## Context

“兼容”取决于模块在接口关系中的角色。只做无方向的接口集合差异，容易把消费者需求变化与提供者能力变化混为一谈，也会使 CI 报告无法说明升级风险。

## Decision

- 比较基线 `old` 与候选版本 `new` 时，显式支持两个方向：
  - `provided`：`new` 是否继续满足旧调用方对导出接口的需求。删除或改变旧导出为 `breaking`；增加导出为 `compatible`。
  - `required`：旧宿主是否仍满足 `new` 的导入需求。增加或改变导入为 `breaking`；移除导入为 `compatible`。
- `both` 同时运行以上两种检查，分别呈现结果，避免把提供能力与外部依赖揉成单一结论。
- 对具备已支持模型且结构相同的条目判为 `compatible`；已识别的删除、增加或类型变化按方向判定；无法比较的条目判为 `unknown` 并附原因。
- 比较优先使用结构化类型和值，不使用类型段序号、函数体内容、地址或未经保证稳定的二进制偏移作为判据。
- MVP 对已支持的类型采用保守规则：类型结构不同视为不兼容，不尝试做未明确实现的子类型推导。新增或复杂类型超出模型能力时返回 `unknown`。
- 总体结果等级固定为 `compatible`、`unknown`、`breaking`。`unknown` 不是兼容成功；默认 CLI 仅在结果为 `compatible` 时返回成功。用户若要忽略 `unknown`，必须通过后续显式选项承担风险。
- MVP 不宣称完整实现 WASM 标准子类型关系、WIT semver 规则或任意宿主 ABI 语义。

## Consequences

- 比较器必须按接口种类和方向应用规则，并对每条变化提供机器可读的类别、标识和原因。
- 文档与命令参数需使用 `provided` / `required` / `both`，不使用有歧义的“向后兼容”单一开关。
- 对复杂引用类型，保守的 `unknown` 可能降低自动化通过率，但可避免错误地报告兼容。

## Verification

- 为新增/删除导入导出、同名类型改变、类型相同但索引不同、以及未支持类型编写正反向测试。
- 对同一组输入，`provided` 与 `required` 可以得出不同且符合定义的结果。
- 默认命令对 `unknown` 以非零状态结束；报告指出未知原因，而不是输出成功。
